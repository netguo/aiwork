一、执行摘要

  1. Agent 评测和传统 LLM 评测是两回事：传统评测评「输出对不对」，Agent 评测评「闭环任务做没做成、过程合不合理、成本划不划算」。业界已收敛到「终态校验（outcome）为主 + 轨迹评测（trajectory）诊断 + LLM-as-Judge 补充 + 人工校准兜底」的组合框架。
  2. 核心指标是 pass@k 与 pass^k 的取舍：pass@k（k 次至少一次成功）衡量峰值能力，pass^k（k 次全部成功）衡量稳定可靠性。生产级 Agent 更应关注 pass^k。
  3. 任务设计五原则：可验证性优先、真实失败案例来源（20-50 个即可起步）、平衡正反例、环境隔离可控、分层难度。
  4. 评测可信度 > 系统复杂度：错误的 LLM 评分器会给 Agent「错误的正反馈」，比没有评测更危险（腾讯技术工程观点，与 Anthropic、NVIDIA 一致）。
  5. 评测是活体资产：需要评估集三分法（train/val/test）、定期刷新防饱和、评测驱动开发（Eval-Driven Development）、与记忆/Skill 更新链路打通形成自进化飞轮。

二、背景：为什么 Agent 评测难

Agent 的自主性带来三个传统软件没有的问题（腾讯 TEG 网关测试团队总结）：

痛点 说明
非确定性 同一 prompt 多次执行结果不同，「跑通一次」不等于「稳定能跑」
黑盒化 模型升级、Prompt 微调、工具链变化都会导致行为漂移，肉眼难以察觉
错误级联放大 一次任务几十步工具调用，前序小偏差沿链路逐级放大，最终结论完全偏离

Anthropic《Demystifying evals for AI agents》进一步指出：让 Agent 有用的能力（自主性、创造性）恰恰使其难以评估——前沿模型能找到超出静态评估设计的创造性解法（如 Opus 4.5 在 τ2-bench 中发现政策漏洞提出更优方案，却按既定标准被判「失败」）。

三、评测框架：谁来评？评什么？评多细？

3.1 三类评分器（谁来打分）

业界共识（Anthropic / OpenAI / 腾讯 TEG / NVIDIA）：没有「银弹评分器」，必须三类组合使用。

确定性评分器 LLM 评分器（Rubric） 人工评分器
谁来评 脚本 / 断言 / Lint / AST 大模型（固定版本） 领域专家
成本 毫秒级 / 免费 秒级 / API 费用 分钟-小时级 / 人力
稳定性 100% 有抖动（需降噪校准） 取决于标注员水平
覆盖 已知硬指标 未知软指标 主观 + 边缘场景
典型用例 文件存在、构建通过、测试通过、工具调用检查 回答质量、意图贴合、解释清晰度 校准 LLM 评委、诊断 0%/100% 异常、红队
角色 硬门禁 分级门禁 采样审查、兜底

选择优先级：确定性评分器 > LLM 评分器 > 人工评分器——能用代码判断的绝不用模型，必要时用模型，人工用于校准。

LLM 评分器的工程要点（Zylos Research、Maxim AI）： - 结构化 Rubric：按维度独立打分（事实准确性 / 任务完成 / 推理质量 / 工具效率 / 沟通清晰度），加权合成，避免「总体打个分」混淆多个正交维度 - 锚点描述：每个维度 1-10 分，在 1/4/7/10 处给出明确锚点描述，减少分数向中间挤压 - 降噪：temperature=0、结构化输出、生成模型与评估模型分离（避免用同一个模型既答又评） - 校准：抽样 100-200 条与人类标注对齐，一致率 ≥ 85% 才算可用；评估器本身需要被「评测」（元评测集） - 给「Unknown」选项：防止 LLM 评委在不确定时强行打分或幻觉

人工评分只投在六个必要场景：校准 LLM 评委（最核心）、主观任务、诊断 0%/100% 通过率异常、建立 Ground Truth、Trace 抽样审查、高风险场景兜底（医疗/金融/安全）。

3.2 五个评测维度（评什么）

从「做对了吗」到「好用吗」逐层递进（腾讯 TEG + TestingXperts + Maxim 汇总）：

大类 核心问题 主要评委 落地优先级
1. 功能正确性 任务做成没 确定性代码 P0
2. 过程质量 过程合理吗（推理、步骤最优、信息完整） Rubric + 人工 P1
3. 效率与成本 划得来吗（Token/步数/延迟/成本） 代码 P1
4. 鲁棒性与安全 关键时刻翻不翻车（pass^k、异常恢复、抗注入、越权） 代码 + 人工 P0
5. 体验与对齐 用户愿意继续用吗（语气、清晰度、主动澄清） Rubric + 人工 P2

关键指标清单（腾讯云社区《Agent 评测方法、工具和指标体系》整理）：

  • 效果指标：Task Success Rate（最核心）、Pass@1、Pass@k、Final Answer Accuracy、Groundedness、Hallucination Rate
  • 工具与轨迹指标：Tool Selection Precision/Recall、Tool Call F1、Parameter Accuracy、Trajectory Efficiency（最优步数/实际步数）、Redundant Call Rate、Loop Rate、Recovery Success Rate
  • 性能与成本指标：TTFT、Time to First Tool、End-to-End Latency（P50/P95/P99）、Token per Task、Cost per Successful Task（优先看这个，低成本但大量失败没有业务意义）

⚠️ 重要提醒：不应机械要求 Agent 轨迹与「黄金轨迹」完全一致——不同路径可能同样正确。通常约束「关键工具、禁止工具、最终状态、最大步数」比逐步匹配更合理。

3.3 评测粒度（评多细）

粒度 成本 用途
粗粒度（整个任务） 便宜 日常回归主力
中粒度（子目标打点） 中 定位阶段失败
细粒度（每个 step） 指数级增长 失败 case 深度归因（按需使用）

建议：日常用粗粒度跑全量，失败 case 用细粒度深度归因（腾讯技术工程）。

四、评测方法：终态校验 vs 轨迹评测 vs LLM-as-Judge

4.1 Outcome（终态校验）优先

核心原则（Anthropic）：优先根据 outcome 评判，不要检查 Agent 是否遵循了特定工具调用顺序——那会惩罚有效的创新路径。

  • 对话 Agent 说「已预订」不算数，环境里的数据库记录才算（腾讯 CT 文章同样强调：最终答案是「结果」，不是「句子」）
  • Computer Use Agent：通过 URL/页面状态检查导航是否正确，通过后端状态确认订单是否真正下达
  • 检查方式优先级：确定性断言 > 状态比对 > LLM 评分 > 人工

4.2 Transcript（轨迹评测）做诊断

轨迹评测评的是执行过程：计划质量、每一步工具调用、推理中间步骤、最终答案与副作用。

  • 两个 Agent 可能给出相同答案，但一个用 3 次精准工具调用，另一个来回震荡几十步——最终答案评分把它们视为相同，生产行为却完全不同（NVIDIA）
  • 计算指标：Trajectory Efficiency、Tool Call Accuracy、failure mode 分布（plan / tool / environment）
  • 关键用途：阅读 transcript 是调试 eval、理解失败原因的唯一途径

4.3 LLM-as-Judge 的定位与边界

  • 用在哪：开放式任务（写作、规划）、主观质量（语气、共情、清晰度）、模拟用户（对话 Agent 的第二 LLM）
  • 已知偏差（Zylos Research 偏差分类法）：
    • 位置偏差（position bias）：成对比较中偏好先出现的答案 → 随机化顺序，关键评估跑两个顺序取平均，分数翻转的 case 转人工
    • 长度偏差（length bias）：系统性高估长回复 → 在 Rubric 中显式说明「长度不是质量信号」
    • 身份偏差：隐藏模型身份，使用不同模型族做裁判集成
    • 裁判过拟合：旋转评委、更换 prompt seed、上线前用人类 gold set 验证
  • Overfitting to judge：Agent 学会「骗过评估器」——评测被黑是真实风险（Anthropic 列举的常见陷阱之一）

4.4 非确定性度量：pass@k vs pass^k

指标 定义 随 k 变化 适用场景
pass@k k 次尝试中至少一次成功 随 k 上升 一次成功即可（编码解题、找方案）
pass^k k 次尝试全部成功 随 k 下降 一致性至关重要（客服、支付、退款、合规等生产场景）

生产系统更关心 pass^k——用户不会接受「多试几次总有一次成功」。

五、评测任务设计：Anthropic 8 步实施路线图

这是目前业界最完整的 Agent 评测落地方法论：

  1. 尽早开始（20-50 个任务就够）：早期系统变化影响明显，小样本足够。不要等「完美套件」。
  2. 从真实失败出发：将手动测试、用户 Bug 报告、支持队列中的真实失败案例转化为测试用例。
  3. 编写无歧义任务 + 参考解决方案：
    • 好任务标准：两位领域专家能独立得出相同的通过/失败结论
    • 参考解决方案证明「任务可解 + grader 配置正确」
    • 若 Agent 在 pass@100 时仍 0% 成功，通常说明是任务或 grader 有问题，而非 Agent 不行
  4. 构建平衡的问题集：同时测试「应该发生」和「不应该发生」的行为，避免单边优化（如过度搜索）。
  5. 构建健壮框架 + 稳定环境：评估中 Agent 行为须与生产一致；每次试验在干净环境隔离运行，避免共享状态污染（Git 历史残留等）。
  6. 精心设计 Grader：确定性优先；多组件任务给部分分数；允许合理创造性解法；LLM 评委需人工校准 + 提供「Unknown」选项。
  7. 检查 Transcripts：读失败案例的轨迹，判断是 Agent 真错了还是 grader 拒绝了有效方案。
  8. 长期维护：通过率接近 100% 时只能跟踪回归、不能提供改进信号（警惕饱和假象）；评估套件是活体资产，需持续刷新。

配套：评估集三分法（腾讯技术工程，与 ML 传统一致）： - train 集：诊断用，可暴露给 LLM - val 集：筛选候选方案，绝不暴露给 LLM - test 集：最终验证，独立

分 Agent 类型差异化评测（Anthropic + Naitive AI）：

Agent 类型 主评测方法 代表性基准
Coding Agent 确定性 grader（单元测试）+ 轨迹 Rubric SWE-bench Verified、Terminal-Bench
Conversational Agent 终态状态检查 + Rubric + 模拟用户第二 LLM τ-bench、τ2-bench
Research Agent Groundedness + Coverage + Source Quality BrowseComp、GAIA
Computer Use Agent 沙盒环境终态检查（DOM/截图权衡） WebArena、OSWorld

七、工业界实践

7.1 腾讯 TEG 网关测试团队

面对非确定性、黑盒化、错误级联三大难题，建立「确定性评分器 + Rubric 评分器 + 人工评分器」三类组合框架，覆盖功能正确性、过程质量、效率成本、鲁棒性安全、体验对齐五维。已在 TPerf 平台智能分析 Agent 落地。核心公式：Eval = Agent 输入 → 执行 → 捕获执行过程（Trace + 产物）→ 一组检查规则 → 可对比的分数。强调用数据代替直觉，用全量代替抽查。

7.2 腾讯「给 Agent 做 CT」体系（可观测 + 质量保障）

  • 数据回流打通观测与评测：离线回流（线上高价值 Trace 周期性清洗转化为评测集）+ 在线回流（点赞/点踩实时反馈）
  • 离线评测（版本上线前新旧对比回归）+ 在线评测（线上持续监控误答率、Token 波动）
  • 评测结果沉淀为优化动作：提示词调整、检索策略优化、模型路由切换
  • 白盒化人工复核页面，针对高价值/高风险场景引入人工标注对齐

7.3 阿里技术专栏（CSDN）

  • 对话 Agent 不能只看单轮答案，须同时看 Turn（单轮）/ Session（整段会话）/ Trace（轨迹）/ Outcome（结果）四层
  • 指标分 P0（上线门禁）/ P1（版本比较）/ P2（体验改善）
  • Skill 本身需要测评：是否该触发、流程对不对、参数是否正确、产物是否可用、异常能否降级
  • 强调「连续成功率」（pass^k）对客服/支付/退款/合规等生产场景的意义

7.4 NVIDIA

五大技巧：① 测 TSR（任务成功率）而非准确率，任务定义为「意图 + 约束」；② 评完整轨迹而非仅最终答案；③ 把工具使用作为一等信号（工具选择 precision/recall、schema 合规）；④ 评分推理质量与效率（token/步数/延迟预算）；⑤ 从第一天就把评测建成透明的工程实践（稳定 ID 记录轨迹、给轨迹打标签）。

7.5 腾讯技术工程：自进化飞轮中的评测

评测在自进化系统中承担方向指引、质量门控、经验筛选三重职责，评测信号直接流入记忆和 Skill 更新链路。诊断归因分四类： - 系统性问题 → 触发 Skill/Prompt 更新 - 偶发个例 → 写入记忆作为反例 - 能力缺失 → 触发工具补充 - 回归问题 → 立即回滚

Skill 评测需通过四层验证才证明「真的有用」：对照实验（无 Skill 时模型是否也会做）、难度校准、轨迹追踪（运行时是否真的调用）、路径验证（绕过关键校验步骤了吗）。

八、常见陷阱清单

  1. 弱评估器（最致命）：LLM 给 LLM 打分存在系统性偏差（偏好长文本、特定格式），错误的正反馈让 Agent 学会「骗过评估器」
  2. 任务规格模糊：grader 检查的前提没在任务描述中明确，Agent 无辜失败
  3. Grader 过于僵化：要求特定工具调用顺序，惩罚了有效的创新路径
  4. Grader 被「黑」：Agent 利用 eval 设计漏洞作弊而不真正解决问题
  5. 任务本身错误：评估者配置错误（如 METR 基准中「优化到指定阈值」的指令与 grader 的「超过阈值」矛盾）
  6. 共享状态污染：实验环境不隔离，前次运行残留影响后续结果
  7. 评估饱和假象：通过率接近 100% 时无法区分能力提升与噪音，产生虚假安全感
  8. 单边评估：只测「应发生」行为，Agent 过度优化导致「不应发生」时也执行
  9. 只报平均分：不报方差、不做多次采样（建议每任务 ≥5 次）
  10. 忽略成本维度：pass@1 高但 token 花 10 倍的方案在生产上不可接受
  11. 评测集漂移：业务变化但评测集不更新，Agent 在旧集刷高分、真实体验下降
  12. 预算不公平：提升可能来自多花 token（如 Best-of-N），须在相同预算下对比
  13. 裁判过拟合与对齐漂移：评测信号无意中奖励「详细」导致 Agent 越来越啰嗦——需要定期方向性审计、约束指标、评测集中显式包含「意图对齐」维度

九、从零到一落地路线建议

9.1 最小闭环（1-2 周）

  1. 收集 20-50 个真实失败案例，写成无歧义任务 + 参考解决方案
  2. 从确定性 grader 开始：单元测试、断言、文件/状态检查、工具调用断言
  3. 搭 CI 门禁，每次 Agent 变更自动跑评测
  4. 阅读失败 transcript，判断是 Agent 错还是 eval 错

9.2 半自动化（2-4 周）

  1. 引入 LLM Rubric 覆盖软指标，抽样 100-200 条人工校准（一致率 ≥ 85%）
  2. 建立评估集三分法（train/val/test）
  3. 加入效率成本指标（token、步数、延迟、Cost per Successful Task）
  4. 引入轨迹评测做失败归因

9.3 生产级（1-2 月）

  1. 在线评测：生产日志抽样、点赞/点踩回流、告警（误答率、token 异常）
  2. 灰度对比（shadow mode / canary / A/B）
  3. 评测驱动的发布门禁：安全失败不发版
  4. 评估集定期刷新，饱和任务「毕业」为回归套件
  5. 打通记忆/Skill 更新链路，形成自进化闭环

9.4 核心原则总结

  • 评测可信度 > 系统复杂度：先把「眼睛」擦亮，再让「手脚」动起来
  • 从终态出发，轨迹诊断，judge 补充，人工校准：四者缺一不可
  • 评测是活体资产：评估集、grader、评测工具都要版本化并持续演进
  • 先跑通手动最小闭环，再逐步自动化
